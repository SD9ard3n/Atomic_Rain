# 资源敏感度分类标准

> **目的**: 防止 Agent 误判未授权访问,区分公开资源和敏感资源
> **原则**: 不是"没鉴权就报",而是"看内容是否敏感"

## 资源分类体系

### 公开资源 (Public) - 无需鉴权是正常的

**定义**: 设计上就应该公开访问的资源,删除 Token 仍可访问是**正常行为**

**典型特征**:
- 面向所有用户公开
- 不包含个人信息
- 不涉及权限控制
- SEO 友好,可被搜索引擎索引

**资源清单**:

| 类型 | 示例 | 判断依据 |
|------|------|---------|
| 新闻/公告 | `/api/news`, `/api/announcements` | 公开内容,面向所有人 |
| 产品信息 | `/api/products`, `/api/pricing` | 营销内容,公开展示 |
| 文档/帮助 | `/api/docs`, `/api/faq`, `/api/help` | 公开文档,无需登录 |
| 健康检查 | `/health`, `/ping`, `/status`, `/version` | 监控端点,必须公开 |
| 静态资源 | CSS/JS/图片/字体 | 前端资源,必须公开 |
| 公开 API 文档 | `/api/swagger`, `/api/openapi.json` | API 文档,公开访问 |
| 注册/登录页 | `/api/register`, `/api/login` | 认证入口,必须公开 |
| 验证码 | `/api/captcha`, `/api/sms/send` | 认证辅助,公开访问 |

**判断标准**:
- ✅ 内容是否面向所有人公开?
- ✅ 是否不包含个人信息?
- ✅ 是否不需要权限控制?

---

### 半公开资源 (Semi-Public) - 需要基础鉴权但不涉及敏感数据

**定义**: 需要登录但不涉及敏感数据,主要是用户自己的非敏感信息

**典型特征**:
- 需要基础认证 (登录)
- 仅返回用户自己的数据
- 数据本身不敏感
- 无权限控制问题

**资源清单**:

| 类型 | 示例 | 判断依据 |
|------|------|---------|
| 用户公开资料 | `/api/user/profile` (昵称/头像) | 用户自己的公开信息 |
| 通用配置 | `/api/config/timezone`, `/api/config/language` | 非敏感配置 |
| 非敏感统计 | `/api/stats/public` (公开统计数据) | 聚合数据,无隐私 |
| 用户偏好 | `/api/user/preferences` (主题/语言) | 个人偏好,非敏感 |

**判断标准**:
- ✅ 是否仅返回用户自己的数据?
- ✅ 数据是否不涉及隐私/财务/权限?
- ✅ 泄露后是否无实际危害?

---

### 敏感资源 (Sensitive) - 必须严格鉴权

**定义**: 包含敏感数据或权限功能,必须严格鉴权,删除 Token 可访问是**漏洞**

**典型特征**:
- 包含他人信息
- 涉及财务/交易
- 管理员功能
- 系统配置/密钥
- 内部 API

**资源清单**:

| 类型 | 示例 | 危害 |
|------|------|------|
| 他人个人信息 | `/api/users/list`, `/api/user/{other_id}` | 隐私泄露 |
| 订单/交易 | `/api/orders`, `/api/transactions` | 财务信息泄露 |
| 支付信息 | `/api/payment/methods`, `/api/wallet` | 财务安全 |
| 管理员功能 | `/api/admin/*`, `/api/manage/*` | 权限提升 |
| 系统配置 | `/api/config/database`, `/api/config/keys` | 系统安全 |
| 内部 API | `/api/internal/*`, `/api/private/*` | 内部信息泄露 |
| 敏感操作 | `/api/user/delete`, `/api/data/export` | 数据安全 |
| 审计日志 | `/api/logs`, `/api/audit` | 安全信息泄露 |

**判断标准**:
- ❌ 是否包含他人信息?
- ❌ 是否涉及财务/交易?
- ❌ 是否为管理员功能?
- ❌ 是否包含系统配置/密钥?

## 未授权访问判断流程

### 标准判断流程

```
步骤 1: 删除 Token/Cookie 访问接口
    ↓
步骤 2: 检查响应状态码
    ├─ 401/403 → 正常,有鉴权 ✅
    └─ 200 → 进入步骤 3
        ↓
步骤 3: 检查返回内容,问自己三个问题:
    Q1: 这个数据是否应该公开? (新闻/产品 = 是)
    Q2: 这个数据是否包含他人信息? (他人订单 = 是)
    Q3: 这个功能是否应该限制权限? (管理员功能 = 是)
        ↓
步骤 4: 判断结果
    ├─ 三个问题都回答"否" → 公开资源,不报告 ✅
    ├─ Q1 是,Q2/Q3 否 → 公开资源,不报告 ✅
    └─ Q2 或 Q3 任一回答"是" → 敏感资源,报告未授权 ❌
```

### 快速判断表

| 场景 | 判断 | 动作 |
|------|------|------|
| `/api/news/list` 返回新闻列表 | 公开资源 | 不报告 ✅ |
| `/api/products` 返回产品列表 | 公开资源 | 不报告 ✅ |
| `/api/config/timezone` 返回时区 | 半公开资源 | 不报告 ✅ |
| `/api/users/list` 返回所有用户 | 敏感资源 | 报告未授权 ❌ |
| `/api/orders/123` 返回他人订单 | 敏感资源 | 报告未授权 ❌ |
| `/api/admin/export` 可访问 | 管理员功能 | 报告未授权 ❌ |

## 判断示例

### 示例 1: 新闻列表 (不报告)

**测试**:
```
DELETE Token
GET /api/news/list
→ 200 OK
→ {"news": [{"title": "产品更新", "content": "..."}]}
```

**判断**:
- Q1: 是否应该公开? → **是** (新闻面向所有人)
- Q2: 是否包含他人信息? → **否**
- Q3: 是否应该限制权限? → **否**

**结论**: 公开资源,不报告 ✅

---

### 示例 2: 用户列表 (报告)

**测试**:
```
DELETE Token
GET /api/users/list
→ 200 OK
→ {"users": [{"id": 1, "name": "张三", "email": "zhang@example.com"}]}
```

**判断**:
- Q1: 是否应该公开? → **否** (用户信息不应公开)
- Q2: 是否包含他人信息? → **是** (包含所有用户信息)
- Q3: 是否应该限制权限? → **是** (应限制为管理员)

**结论**: 敏感资源,报告未授权访问 ❌

---

### 示例 3: 健康检查 (不报告)

**测试**:
```
DELETE Token
GET /health
→ 200 OK

```

**判断**:
- Q1: 是否应该公开? → **是** (监控端点必须公开)
- Q2: 是否包含他人信息? → **否**
- Q3: 是否应该限制权限? → **否**

**结论**: 公开资源,不报告 ✅

### 示例 4: 管理员导出 (报告)

**测试**:
```
DELETE Token
GET /api/admin/export
→ 200 OK
→ 开始下载 users.csv
```

**判断**:
- Q1: 是否应该公开? → **否**
- Q2: 是否包含他人信息? → **是** (导出所有用户数据)
- Q3: 是否应该限制权限? → **是** (管理员功能)

**结论**: 敏感资源,报告未授权访问 ❌

---

### 示例 5: 用户自己的资料 (边界情况)

**测试**:
```
DELETE Token
GET /api/user/profile
→ 200 OK
→ {"nickname": "测试用户", "avatar": "https://..."}
```

**判断**:
- Q1: 是否应该公开? → **否** (需要登录)
- Q2: 是否包含他人信息? → **否** (仅自己的公开资料)
- Q3: 是否应该限制权限? → **是** (需要登录)

**结论**: 
- 如果返回的是**公开资料** (昵称/头像) → 半公开资源,**可以报告为 Low**
- 如果返回的是**敏感信息** (手机号/邮箱) → 敏感资源,**报告为 High**

## 特殊情况处理

### 情况 1: 分页接口

**场景**: `/api/users?page=1&size=10` 返回用户列表

**判断**:
- 即使只返回 10 条,仍然是**敏感资源**
- 可以通过翻页获取所有用户 → 报告未授权

### 情况 2: 搜索接口

**场景**: `/api/search?q=admin` 返回包含 "admin" 的用户

**判断**:
- 如果搜索**公开内容** (新闻/产品) → 公开资源
- 如果搜索**用户信息** → 敏感资源,报告未授权

### 情况 3: 统计接口

**场景**: `/api/stats/users` 返回 `{"total": 10000}`

**判断**:
- 如果仅返回**聚合数据** (总数/平均值) → 半公开资源,不报告
- 如果返回**明细数据** (具体用户列表) → 敏感资源,报告未授权

### 情况 4: 内部 API

**场景**: `/api/internal/metrics` 返回系统指标

**判断**:
- 路径包含 `internal` / `private` / `admin` → **默认为敏感资源**
- 即使内容看似无害,仍应报告 (内部 API 不应公开)

## 集成到 Decision Card

在未授权访问的 Decision Card 中添加:

```markdown
## 未授权访问判断协议

**步骤 1**: 删除 Token 访问
**步骤 2**: 返回 200 → 进入敏感度判断
**步骤 3**: Grep `resource-classification.md` 查询资源分类
**步骤 4**: 问自己三个问题:
  - Q1: 这个数据是否应该公开?
  - Q2: 这个数据是否包含他人信息?
  - Q3: 这个功能是否应该限制权限?
**步骤 5**: 三个问题任一回答"是" → 确认未授权

**禁止**:
- 看到 200 就报"未授权访问"
- 不检查内容就报告
- 把公开资源当成未授权
```

## 自我检查清单

在报告未授权访问前,问自己:

- [ ] 是否已删除 Token 测试?
- [ ] 返回状态码是否为 200?
- [ ] 是否已检查返回内容?
- [ ] 是否已查询 resource-classification.md?
- [ ] 是否已回答三个判断问题?
- [ ] 是否排除了公开资源 (新闻/产品/文档)?
- [ ] 是否排除了健康检查端点?
