# 信息敏感度评分标准

> **目的**: 防止 Agent 误判信息泄露,通过三维评分量化敏感度
> **原则**: 不是"有信息就报",而是"评估影响再报"

---

## 🚀 快速判断法 (Agent 优先使用)

> **适用场景**: Agent 快速判断,无需复杂计算
> **执行时间**: < 5秒

### 判断流程

```
Step 1: 是否是凭证类?
├─ 密码/Token/AK/SK/私钥/API Key
└─ 是 → 临时 T-Critical ⚠️ (必须验证后才可报告, 见下注)

Step 2: 是否是身份类?
├─ 身份证/手机号/邮箱/真实姓名/地址
└─ 是 → 报告 High ✅ (无需继续)

Step 3: 是否是业务类?
├─ 订单详情/交易金额/用户行为/聊天记录
└─ 是 → 报告 High ✅ (无需继续)

Step 4: 是否是技术类?
├─ 内部路径/数据库结构/中间件版本/源码片段
└─ 是 → 检查版本年份
    ├─ 版本 ≥ 2年前 → 报告 Medium
    └─ 版本 < 2年 → 不报告

Step 5: 其他
└─ 产品版本/公司名称/时间戳 → 不报告
```

### 快速判断示例

**示例 1**: `{"server": "nginx/1.18.0"}`
```
Step 1: 凭证类? 否
Step 2: 身份类? 否
Step 3: 业务类? 否
Step 4: 技术类? 是 → 版本 nginx/1.18.0 (2020年)
        → 距今 6年 ≥ 2年 → 报告 Medium
```

**示例 2**: `{"aws_access_key": "AKIA..."}`
```
Step 1: 凭证类? 是 → 临时 T-Critical ⚠️ (需验证)
```

**示例 3**: `{"version": "1.0.0"}`
```
Step 1-4: 都不是
Step 5: 产品版本 → 不报告
```

## 📊 三维评分法 (可选,用于复杂场景)

> **适用场景**: 快速判断法无法判断时使用
> **执行时间**: 需要详细评估

### 评分维度 (三维评估)

### 维度 1: 信息类型 (0-10 分)

| 分值 | 类型 | 示例 | 说明 |
|------|------|------|------|
| 10 分 | 凭证类 | 密码/Token/AK/SK/私钥/API Key | 可直接用于身份认证或授权 |
| 8 分 | 身份类 | 身份证/手机号/邮箱/真实姓名/地址 | 个人隐私信息,可用于社工 |
| 6 分 | 业务类 | 订单详情/交易金额/用户行为/聊天记录 | 业务敏感数据,影响用户隐私 |
| 4 分 | 技术类 | 内部路径/数据库结构/中间件版本/源码片段 | 技术实现细节,可能辅助攻击 |
| 2 分 | 公开类 | 产品版本/公司名称/公开文档/通用配置 | 公开或半公开信息 |
| 0 分 | 无价值 | 时间戳/通用错误码/HTTP状态码 | 无安全价值 |

### 维度 2: 可利用性 (+0 到 +3 分)

| 分值 | 可利用性 | 示例 | 判断标准 |
|------|---------|------|---------|
| +3 分 | 可直接利用 | 明文密码/有效Token/未过期AK | 拿到即可直接使用 |
| +2 分 | 可间接利用 | 路径可用于LFI/版本有已知CVE/数据库结构可用于注入 | 需要配合已知漏洞利用 |
| +1 分 | 需组合利用 | 用户名列表(需配合爆破)/内部IP(需配合SSRF) | 需要配合其他漏洞或攻击手段 |
| 0 分 | 无法利用 | 已失效Token/无攻击面的版本号/无CVE的中间件 | 当前无法利用 |

### 维度 3: 影响范围 (+0 到 +2 分)

| 分值 | 影响范围 | 示例 | 判断标准 |
|------|---------|------|---------|
| +2 分 | 影响所有用户/系统 | 云账号AK/数据库密码/管理员Token | 可控制整个系统或所有用户数据 |
| +1 分 | 影响单个用户/模块 | 单个用户Token/单个订单信息 | 仅影响特定用户或模块 |
| 0 分 | 无实际影响 | 测试账号信息/已下线功能的配置 | 不影响生产环境或真实用户 |

---

## 报告阈值

### 总分计算

```
总分 = 维度1 (信息类型) + 维度2 (可利用性) + 维度3 (影响范围)
```

### 报告规则

| 总分 | 等级 | 动作 | 说明 |
|------|------|------|------|
| ≥ 8 分 | Critical | 立即报告 | 高危信息泄露,需立即修复 |
| 6-7 分 | High | 报告 | 重要信息泄露,应尽快修复 |
| 4-5 分 | Medium | 记录到 assets.md,不单独报告 | 技术信息泄露,记录备用 |
| ≤ 3 分 | Low | 忽略 | 无安全价值或公开信息 |

## 评估示例

### 示例 1: nginx 版本号

**发现**: `{"server": "nginx/1.18.0"}`

**评估**:
- 维度1 (信息类型): 技术类 → **4 分**
- 维度2 (可利用性): 查询 CVE,nginx 1.18.0 无已知高危漏洞 → **0 分**
- 维度3 (影响范围): 无实际影响 → **0 分**
- **总分**: 4 分

**结论**: Medium,记录到 assets.md,不单独报告

---

### 示例 2: AWS Access Key

**发现**: `{"aws_access_key": "AKIAIOSFODNN7EXAMPLE"}`

**评估**:
- 维度1 (信息类型): 凭证类 → **10 分**
- 维度2 (可利用性): 可直接利用 → **+3 分**
- 维度3 (影响范围): 影响整个云账号 → **+2 分**
- **总分**: 15 分

**结论**: Critical,立即报告

---

### 示例 3: 用户名列表

**发现**: `{"users": ["admin", "test", "user1", "user2"]}`

**评估**:
- 维度1 (信息类型): 身份类 (用户名) → **8 分**
- 维度2 (可利用性): 需组合利用 (配合爆破) → **+1 分**
- 维度3 (影响范围): 影响所有用户 → **+2 分**
- **总分**: 11 分

**结论**: Critical,立即报告

---

### 示例 4: 内部路径

**发现**: `{"error": "File not found: /var/www/html/app/config/database.php"}`

**评估**:
- 维度1 (信息类型): 技术类 (内部路径) → **4 分**
- 维度2 (可利用性): 可间接利用 (可用于 LFI) → **+2 分**
- 维度3 (影响范围): 影响单个模块 → **+1 分**
- **总分**: 7 分

**结论**: High,报告

---

### 示例 5: 产品版本

**发现**: `{"version": "1.0.0", "build": "20260425"}`

**评估**:
- 维度1 (信息类型): 公开类 → **2 分**
- 维度2 (可利用性): 无法利用 → **0 分**
- 维度3 (影响范围): 无实际影响 → **0 分**
- **总分**: 2 分

**结论**: Low,忽略

---

### 示例 6: 数据库结构

**发现**: SQL 报错泄露表结构 `Table 'users' doesn't exist in database 'production'`

**评估**:
- 维度1 (信息类型): 技术类 (数据库结构) → **4 分**
- 维度2 (可利用性): 可间接利用 (辅助 SQLi) → **+2 分**
- 维度3 (影响范围): 影响所有用户 → **+2 分**
- **总分**: 8 分

**结论**: Critical,立即报告

## 强制评估流程

### Agent 执行协议

发现任何信息泄露时,**禁止**直接报告,**必须**先执行三维评估:

```
步骤 1: 识别信息类型 → 查表得分 (0-10)
步骤 2: 评估可利用性 → 查表得分 (+0 到 +3)
步骤 3: 评估影响范围 → 查表得分 (+0 到 +2)
步骤 4: 计算总分 = 步骤1 + 步骤2 + 步骤3
步骤 5: 根据总分决定动作:
  - ≥ 8 分 → 立即报告 Critical
  - 6-7 分 → 报告 High
  - 4-5 分 → 记录到 assets.md,标记 [Info_Leak_Medium]
  - ≤ 3 分 → 忽略
```

### 集成到 SKILL.md

在 `SKILL.md` 的 P2 阶段添加:

```markdown
## P2: 信息敏感度评估 (Sensitivity Check)

发现任何信息泄露时,**必须**先执行三维评估:

1. Grep `sensitivity-matrix.md` 查询评分标准
2. 计算总分 = 信息类型 + 可利用性 + 影响范围
3. 总分 ≥ 6 才报告,否则记录或忽略

**禁止**:
- 看到版本号就报"信息泄露"
- 看到错误信息就报"敏感信息泄露"
- 不评估直接报告
```

## 特殊情况处理

### 情况 1: 组合信息泄露

如果单个信息不敏感,但多个信息组合后敏感度提升:

**示例**: 
- 单独泄露 `{"username": "admin"}` → 8+1+1 = 10 分 (Critical)
- 单独泄露 `{"password_hash": "md5"}` → 4+1+0 = 5 分 (Medium)
- **组合泄露** → 按最高分报告 (Critical)

### 情况 2: 上下文相关

同样的信息在不同上下文中敏感度不同:

**示例**:
- 公开 API 文档中的 `/api/users` → 2+0+0 = 2 分 (Low)
- 错误信息泄露的 `/api/internal/admin/users` → 4+2+2 = 8 分 (Critical)

### 情况 3: 时效性

信息的时效性影响可利用性:

**示例**:
- 有效期内的 Token → 10+3+2 = 15 分 (Critical)
- 已过期的 Token → 10+0+0 = 10 分 (仍然 Critical,因为泄露了凭证格式)

## 自我检查清单

在报告信息泄露前,问自己:

- [ ] 是否已查询 sensitivity-matrix.md 评分标准?
- [ ] 是否已计算三维总分?
- [ ] 总分是否 ≥ 6 分?
- [ ] 是否考虑了可利用性 (能否直接/间接利用)?
- [ ] 是否考虑了影响范围 (影响多少用户/系统)?
- [ ] 是否排除了公开信息 (产品版本/公司名称)?
